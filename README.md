# 航道对外服务智能体

> 当前阶段：双 RTX 5090 服务器 RAG 基线已验证，进入正式数据治理与预处理
> 最近更新：2026-09-21

本项目拟建设一个面向船东企业、工程建设单位、设计院、沿江港航企业及社会公众的航道对外服务智能体。第一阶段以千问系列模型为核心，通过 RAG（检索增强生成）连接航道专业资料，先实现答案可追溯的知识问答；随后再接入实时航道数据和业务系统，逐步实现办事指引、航评咨询、事项进度查询和定向信息推送。

需求来源：本地原始资料 `profile/对外服务智能体初步建设需求.docx`，该目录不纳入版本库。

## 本地最小 RAG 已实现

当前代码已经打通以下最小闭环：

```text
本地文档
  → 解析与分段
  → Qwen3-Embedding-0.6B 向量化
  → 本地 JSON 向量索引
  → 向量与关键词混合检索
  → Qwen3.5-9B 依据证据生成答案
  → 返回 [S1] 引用和来源片段
```

为了避免把历史信息冒充实时信息，当前版本会直接拦截实时水深、水位、气象、航道管制和审批进度问题。后续接入权威业务接口后，再将这些问题路由到实时工具。

### 2026-09-21 已验证基线

- 实验室双 RTX 5090 服务器已经部署 `qwen3.5:9b` 和 `qwen3-embedding:0.6b`。
- 28 份代表性资料已生成 541 个索引片段。
- 由 `initial-20.jsonl` 与 `expanded-30.jsonl` 组成的 50 题评测集通过 50 题，失败 0 题。
- 当前 49 项单元测试全部通过。
- 平均完整响应时间约 0.98 秒，中位数约 0.92 秒，最大约 4.38 秒；该结果仅代表单用户、当前样本和当前服务器，不是生产并发指标。
- 已验证法规、标准、历史公共服务信息、PDF 表格、XLSX 目录、跨文档比较、无答案拒答和实时问题拦截。

当前基线用于后续数据处理回归。增加资料、修改解析方式或调整参数后，都必须重新运行同一套
50 题评测，不能只凭个别问答判断效果。

### 1. 准备本地环境

要求 Python 3.9 或更高版本，并确保 Ollama 已启动：

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -r requirements.txt

brew services start ollama
ollama pull qwen3.5:9b
ollama pull qwen3-embedding:0.6b
```

复制配置文件；默认值已经适合当前 Mac，本步骤也可以暂时跳过：

```bash
cp .env.example .env
```

默认 `RAG_MIN_SCORE=0.45`：相关度低于该值的检索片段不会交给大模型；
若所有候选片段都低于阈值，接口会直接返回“现有知识库无法确认”并保持来源列表为空。
后续只能根据业务评测集调整该值，不能为了提高回答率随意降低。

### 2. 审计和预处理真实资料

先生成文档台账，每份 PDF 抽样检查前 5 页：

```bash
python -m scripts.audit_documents profile --pdf-page-limit 5
```

需要逐页确认时使用 `--pdf-page-limit 0`。结果保存到被 Git 忽略的
`data/manifests/document-audit.jsonl`。

对已选择的少量样本执行标准化：

```bash
python -m scripts.preprocess "profile/已确认的首批样本目录"
```

命令会将可提取内容写入 `data/processed/`，并将文件标记为 `ready`、
`needs_ocr`、`partial_needs_ocr`、`partial_needs_image_ocr`、`needs_conversion`
或 `unsupported`。

需要实际执行 OCR 时，使用独立的 Python 3.12 环境。轻量后端适合本机功能验证：

```bash
.venv-ocr/bin/python -m scripts.preprocess "profile/已确认的扫描样本.pdf" \
  --ocr-backend paddleocr \
  --ocr-device cpu
```

双 RTX 5090 服务器在管理员确认 CUDA 12.9 驱动兼容后，才使用
`--ocr-backend paddleocr-vl --ocr-device gpu:0`，以保留表格、标题和阅读顺序。
项目会拒绝 VL+CPU 或无可见 CUDA GPU 的运行方式；16 GB Mac 上不要再尝试 VL 推理。
详细安装及验收步骤见 [OCR 部署手册](docs/OCR部署手册.md)。

### 3. 构建演示知识库

先用 README 自身验证流程，不读取整批原始资料：

```bash
python -m scripts.ingest README.md
```

需要测试真实资料时，应明确选择少量已确认可用的文件。每次执行导入命令都会用本次指定的资料重建索引：

```bash
python -m scripts.ingest \
  "profile/材料一/法律法规等/某份资料.docx" \
  "profile/材料一/技术标准等（第一部分）/某份标准.pdf"
```

当前解析器支持 `.md`、`.txt`、文本型 `.pdf`、`.docx` 和 `.xlsx`。扫描 PDF 和
DOCX 内嵌图片可在独立 OCR 环境中处理；旧版 `.doc` 需要先转换为 DOCX 或 PDF。

### 5. 运行自动测试

```bash
python -m unittest discover -v
```

这个版本面向单机 PoC：JSON 向量索引适合小批量样本文档，不适合作为生产数据库；
已接入可选 OCR 后端，但还没有重排模型、用户认证、多轮会话、运营后台和实时业务接口。

2026-09-17 已用 PP-OCRv5 mobile 成功处理一份 3 页真实扫描 PDF，得到 2,410 个字符和
3 个页级来源片段。轻量后端会丢失复杂表格的行列关系，不能代替正式的 PaddleOCR-VL 验收。

## 一句话结论

这个项目不能只做“把文档放进向量库后聊天”。完整需求至少包含四类能力：静态知识库、实时数据查询、政务事项流程和主动服务。建议先做一个范围可控、答案带出处的知识库问答 MVP，再逐步接入动态数据与业务流程。

## 需求分析

### 1. 航道专业知识库与公共服务名录

- 建设技术标准库、航道基础信息库、航评案例库和法规政策库。
- 建设公共服务名录，维护服务事项、办理条件、材料清单、办理时限、责任部门和联系方式。
- 将“知识查询”和“事项办理指引”关联起来。

### 2. 7×24 小时航道信息问答

- 支持自然语言问答、多轮对话、上下文理解和必要的追问。
- 覆盖航道尺度、水深、航标、航行通告、航道管制、水位、政策和办事信息。
- 记录问题、检索结果、用户反馈和热点主题，供知识库持续优化。

### 3. 公共服务解答

- 对法规、政策和技术标准进行检索、引用和通俗化解释。
- 为专用航标设置或调整、航评咨询等事项提供分步骤指引。
- 后续按用户类型和业务场景推送政策更新、标准修订及宣传内容。

### 4. 定制化涉航技术服务

- 根据桥梁、管线、码头等工程类型提供航评咨询。
- 接收项目初步方案，依据法规和标准生成辅助合规检查结果、相似案例和风险提示。
- 按船东企业、沿江港航企业和社会公众建立不同的服务内容与订阅规则。
- 对事项受理、审核和办结节点进行进度提醒。

### 能力边界

| 能力 | 正确实现方式 | 不能只依赖什么 |
| --- | --- | --- |
| 法规、标准、历史报告问答 | 文档解析、混合检索、重排、千问生成、原文引用 | 仅靠模型自身知识 |
| 水深、水位、气象、管制等实时信息 | 对接权威数据库或 API，并返回数据时间 | 定期上传的静态文件 |
| 办理条件和材料清单 | 结构化公共服务名录，并设置责任部门审核和版本生效时间 | 从长文中临时生成 |
| 审批进度查询和节点提醒 | 对接业务办理系统、用户身份和消息渠道 | 向量数据库 |
| 项目方案合规检查 | 文件解析、规则检索、结构化检查项和人工复核 | 让大模型直接作最终合规结论 |
| 定向政策推送 | 用户标签、订阅授权、规则引擎和消息发送能力 | 普通聊天会话 |

智能体应定位为查询、咨询和辅助判断工具。法规解释、合规检查和审批事项必须展示依据、文件版本和数据时间；高风险结果应交由业务人员复核，不能替代法定审批或专业结论。

### 适合建立的知识集合

不要沿用“材料一”和“材料二”作为最终知识库名称，建议按业务语义重组为：

1. `technical_standards`：合并两部分技术标准，按标准号、名称、发布年份、状态和适用场景检索。
2. `laws_and_policies`：法律法规与管理规定，按效力层级、发布机关、地域、发布日期、生效日期和有效状态管理。
3. `channel_public_information`：公共服务信息、维护尺度、养护计划、运行报告和通告，重点管理航段及时间范围。
4. `service_catalog`：办事事项、条件、材料、时限、责任部门、联系方式和流程节点，优先结构化存储。
5. `navigation_assessment_cases`：需求中要求的航评报告、审批意见和典型案例；现有文件名中未看到明确、完整的案例集合，需要另行补充。

### 从文件名发现的数据治理问题

- 公共服务资料覆盖 2018—2026 年，并同时存在年度、月度和计划类文件。检索时必须优先匹配航段、适用年月、发布日期和最新有效版本，不能把历史值当成当前值。
- 法规文件通常用日期后缀标识版本，但部分名称的日期为空，如 `福建省航道条例_.docx`。需要从正文或权威台账补齐发布日期、生效日期、修订状态和效力状态。
- 技术标准文件名包含 `+`、序号、逗号及下载编号等噪声，标准号写法也不统一。入库前要规范化标题和标准编号，同时保留原始文件名。
- 存在旧版 `.doc` 文件，解析链路需要先转换为 DOCX 或 PDF。
- `2025 年度长江干线主航道养护尺度标准` 缺少扩展名，应先确认实际格式和文件完整性。
- PDF 可能包含扫描页、复杂表格和跨页表格。正式入库前必须进行可解析性检测，并为扫描件配置 OCR 和表格抽取。
- Excel 目录清单适合做台账入口，但未核对内容前不能默认它们与实际文件一一对应。


## 初步技术方案

```text
Web 或政务服务入口
        │
        ▼
认证、限流与会话 API
        │
        ▼
智能体编排层
  ├─ 意图识别与问题改写
  ├─ 知识库检索与重排
  ├─ 实时数据和业务系统工具调用
  ├─ 权限、时效与风险校验
  └─ 千问生成带依据的回答
        │
        ├─ 文档库、向量索引和元数据数据库
        ├─ 数字航道、水位气象、航行通告等接口
        ├─ 服务事项与审批进度接口
        └─ 日志、反馈、评测与运营分析
```

建议将模型服务、检索服务和业务系统连接器解耦。上层统一使用兼容 OpenAI 风格的模型接口，便于在千问不同型号、部署方式和后续升级之间切换，避免业务代码绑定某个具体模型。

### 千问模型策略

- 当前 Mac 使用 `Qwen3.5-9B Q4_K_M` 负责回答，使用 `Qwen3-Embedding-0.6B` 负责向量化。
- 本机模型用于接口、提示词、检索和评测链路开发，不直接代表最终生产效果。
- 实验室双 RTX 5090 服务器优先测试 `Qwen3.5-27B`，并将 `Qwen3.5-35B-A3B` 作为吞吐和效果对照；实际量化和并行策略以服务器 `nvidia-smi`、驱动、显存与 PCIe 拓扑实测为准。
- 服务器模型服务建议使用 vLLM，业务层继续使用兼容 OpenAI 风格的接口，避免绑定具体部署方式。
- MVP 上下文先控制在 8K—16K。更长上下文会增加显存和延迟，不能替代正确的文档切分、检索与重排。
- 向量模型和重排模型应独立评测，重点检查中文法规、标准号、航段名、数值和表格内容的召回能力。

参考官方入口：[Qwen3](https://github.com/QwenLM/Qwen3)、[Qwen3.5-27B](https://huggingface.co/Qwen/Qwen3.5-27B)、[Qwen3.5-35B-A3B](https://huggingface.co/Qwen/Qwen3.5-35B-A3B)。

### 建议的基础组件

| 模块 | 初步选择 | 说明 |
| --- | --- | --- |
| 大模型 | 千问系列指令模型 | 负责回答生成、问题改写、意图识别和工具调用 |
| 推理服务 | 本地 Ollama，服务器 vLLM | 上层保持兼容 API，便于模型切换 |
| 文档处理 | PDF、DOCX、DOC、XLSX 解析 + OCR | 保留页码、标题层级、表格和来源信息 |
| 检索 | 关键词检索 + 向量检索 + 重排 | 标准号、法规名和精确数值不能只靠向量召回 |
| 元数据与业务数据 | 关系型数据库 | 管理版本、时效、权限、服务事项和用户订阅 |
| 向量索引 | 选用支持元数据过滤的向量数据库 | 产品待结合现有技术栈和运维能力确定 |
| 接口层 | HTTP API + 流式输出 | 隔离模型、知识库和外部业务系统 |
| 观测与评测 | 请求日志、链路追踪、离线评测集 | 监测召回、引用、延迟、失败和用户反馈 |

## 实施顺序

### 阶段 0：补齐前置条件

- 确认首批服务对象、访问入口、内外网部署方式和身份认证方式。
- 获取数字航道、航行通告、水位气象、事项办理和消息推送系统的接口清单。
- 获取服务器实际 OS、NVIDIA 驱动、CUDA、显存和 `nvidia-smi topo -m` 信息。
- 明确哪些资料可以对公众开放，哪些只允许内部用户访问。
- 由业务部门确定法规、标准、公共服务信息的权威来源和审核责任人。

### 阶段 1：知识库问答 MVP

建议先只做“静态资料问答”，完成一条可验证的最小闭环：

1. 从四类资料中各选一批代表性文件，覆盖文本 PDF、扫描 PDF、表格 PDF、DOCX、DOC 和 XLSX。
2. 建立资料台账，完成格式识别、OCR、正文与表格抽取、标题规范化和元数据补齐。
3. 实现分类型切分、关键词与向量混合检索、重排及来源引用。
4. 接入千问，要求回答仅依据检索结果；证据不足时明确拒答或请求补充信息。
5. 提供一个简单对话页面或 API，支持流式回答、多轮上下文和来源查看。
6. 建立业务评测集，覆盖精确查找、跨文档比较、历史与现行版本区分、数值问答、无答案拒答和提示注入攻击。
7. 由业务人员审核结果，根据失败案例调整解析、元数据、召回和提示词。

MVP 的交付物应包括：资料台账、入库流水线、可重复构建的索引、带引用的问答接口、基础对话页面、评测数据集和评测报告。

### 阶段 2：公共服务名录

- 将办事条件、材料、时限、部门和联系方式从文档整理为结构化数据。
- 实现按用户场景逐步追问，并生成办理清单。
- 对每项服务设置版本、生效时间、审核人和修改记录。

### 阶段 3：动态数据与业务系统

- 通过工具调用接入水深、水位、气象、航标、航行通告和航道管制等权威接口。
- 回答中明确数据来源和更新时间；接口失败时不得用历史知识冒充实时结果。
- 接入事项办理系统，实现进度查询与节点提醒。

### 阶段 4：定制化服务

- 建立用户标签、订阅、授权和退订机制。
- 实现政策更新、风险预警和服务简报的定向推送。
- 实现项目方案上传、文本抽取、检查项匹配、相似案例检索和人工复核工作台。
- 在业务审核后再生成对外宣传图文，避免模型未经复核直接发布。

## 你现在要做什么

按优先级完成以下工作即可启动项目：

1. 找业务负责人确认 MVP 是否先聚焦“法规、规定、技术标准和历史公共服务信息问答”。
2. 索取航评案例、公共服务事项完整名录，以及各动态业务系统的接口文档和样例数据。
3. 在双 RTX 5090 服务器记录 `nvidia-smi`、CUDA、系统内存、磁盘和 GPU 拓扑，并实测 27B 模型。
4. 指定每类知识资料的审核人，确认公开范围、现行版本和更新流程。
5. 从现有资料中选取约 20—30 份代表性文档作为首批样本，不要一次性导入全部资料。
6. 与业务专家共同编写首批真实问题及标准答案，用它们选择模型、检索和切分方案。
7. 确认预期并发、响应时间、可用性、部署网络和日志留存要求，再确定生产架构。

## 待确认问题

- 系统最终面向公网、政务外网、内网，还是同时支持多个入口？
- 是否存在统一用户体系，是否需要实名、企业认证和分级授权？
- 哪些数据是实时数据，其权威接口、刷新频率和失败兜底规则是什么？
- 公共服务名录由哪个部门维护，是否已有结构化系统？
- 是否需要直接提交申请，还是第一期只提供材料和流程指引？
- 政策推送使用短信、微信、网站消息还是其他渠道？
- 上传的项目方案可能包含哪些敏感信息，保存多久，谁可以查看？
- 答案是否必须逐条引用到页码或法规条款，业务人员如何纠错和发布新版本？
- 目标并发、首字延迟、峰值请求量和故障恢复指标是多少？
- 千问模型必须完全离线部署，还是允许 MVP 阶段调用受控的云端 API？

## 初步验收指标

正式数值需要和业务方确认，至少应覆盖：

- 文档解析成功率、OCR 可读率和表格抽取正确率。
- 检索召回率、重排质量和无答案识别率。
- 回答事实准确率、引用正确率、现行版本识别率和数值准确率。
- 实时数据来源与更新时间展示完整率。
- 首字延迟、完整响应时间、吞吐、并发和服务可用性。
- 越权访问、敏感信息泄露、提示注入和恶意文件上传防护。
- 用户反馈闭环、知识更新时延和问题热点统计能力。

## 安全与质量要求

- 知识入库、模型服务和用户访问都要进行权限隔离。
- 对上传文件做扩展名、MIME、大小、病毒和恶意内容检查。
- 防止知识库文档或用户输入中的提示注入改变系统规则。
- 对回答保存问题、检索证据、模型版本、提示版本、工具调用和输出，便于审计。
- 动态数值必须带时间戳；历史资料必须标识数据期；失效法规和标准不得作为现行依据。
- 对外答案默认附来源。没有可靠证据时明确说明无法确认，不生成貌似确定的结论。
- 用户画像和主动推送必须取得授权，并提供退订与数据删除机制。

## 后续生产化仓库结构

当前 MVP 使用前文所示的轻量目录。进入多人开发和生产化阶段后，建议逐步拆分为：

```text
.
├── README.md
├── docs/                  # 需求、架构、接口、数据字典和评测说明
├── data/
│   ├── raw/               # 原始资料，只读保存
│   ├── manifests/         # 文档台账与元数据
│   └── evals/             # 评测问题、标准答案和证据
├── src/
│   ├── api/               # 对话与管理 API
│   ├── agent/             # 智能体编排、提示词和工具调用
│   ├── ingestion/         # 解析、OCR、清洗、切分和入库
│   ├── retrieval/         # 混合检索、重排和引用
│   └── connectors/        # 数字航道及业务系统连接器
├── tests/                 # 单元、集成、安全和离线评测
└── deploy/                # 容器、GPU/NPU 环境配置和运维脚本
```

原始资料不建议直接提交到后续公开代码仓库；应根据数据权限放入受控存储，并仅在台账中保存受控引用。

该服务器作为当前首选模型验证环境，先用 `Qwen3.5-9B` 跑通部署，随后评估
