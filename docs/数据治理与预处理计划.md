# 数据治理与预处理计划

> 更新日期：2026-09-21
> 当前目标：将候选原始资料按权限和批次转换为可追溯、可检查、可重复构建的知识库输入

## 1. 为什么现在进入这个阶段

当前 28 份代表性资料已经生成 541 个索引片段，服务器固定评测达到 50/50。该结果证明最小
RAG 链路可以工作，但尚不代表全部候选资料可直接入库。现有 287 份候选资料同时包含文本型
PDF、扫描 PDF、混合 PDF、DOCX 图片、旧版 DOC、复杂表格和不同历史版本，下一阶段应先做
数据治理与预处理，再扩大知识库。

正式处理遵循三个原则：

1. 原始文件只读保存，预处理结果写入新目录，不覆盖原件。
2. 公开、内部和敏感资料分开处理、分开建索引；当前应用没有用户级权限过滤，不能混库。
3. 每次只处理一个可回滚批次，并使用固定评测集检查是否造成质量退化。

当前 API 正在局域网监听 `0.0.0.0:8001` 且没有身份认证，因此现阶段只能向这个实例导入
已经确认允许同一局域网测试人员查看的资料。内部或敏感资料必须等待认证和权限过滤完成，或
使用完全隔离且不对其他用户开放的实例。

## 2. 正式处理前需要业务方确认

每份资料至少确认以下内容：

| 字段 | 需要确认的内容 |
| --- | --- |
| `document_id` | 稳定且唯一的资料编号 |
| `title` | 规范标题 |
| `original_filename` | 原始文件名，不得丢失 |
| `knowledge_collection` | 法规、规定、标准、公共服务信息、服务名录或案例 |
| `access_level` | 公开、内部或敏感 |
| `effective_status` | 现行、失效、废止、草案或待确认 |
| `publish_date` / `effective_date` | 发布和生效时间 |
| `valid_from` / `valid_to` | 数据适用时间，月度和年度资料尤其重要 |
| `issuer` | 发布机关或责任部门 |
| `reviewer` | 业务审核人 |
| `source_uri` | 权威来源或受控存储位置 |
| `checksum` | 用于发现文件是否发生变化 |

无法确认权限、版本或审核人的资料可以完成技术审计，但不能进入对外索引。

## 3. 建议的受控目录

服务器上使用代码仓库之外的受控目录保存原件。例如：

```text
/home/shuncs/rag-data/
├── raw/                 # 原始文件，只读保存
│   ├── public/
│   ├── internal/
│   └── sensitive/
├── batches/             # 每次处理的文件清单或受控副本
│   └── batch-001/
├── processed/           # 标准化 Markdown 和 OCR 结果
│   └── batch-001/
├── manifests/           # 审计、预处理、元数据与质检台账
├── indexes/             # 按权限和版本生成的索引
└── archive/             # 已替换但需要留存的历史版本
```

代码仓库中的 `profile/`、`data/processed/`、`data/manifests/` 和 `data/index.json` 均被 Git
忽略，但“被 Git 忽略”不等于具备数据安全能力。正式原件仍应放在受控目录并设置最小权限。

## 4. 每个批次的完整处理流程

项目已经提供 `scripts.build_knowledge_base` 统一编排下述步骤。它会在每份文件完成后保存断点，
重复执行时跳过未变化且已经成功的文件；扫描件不会被静默忽略。没有启用 OCR 时，扫描件会
进入 `needs_ocr` 队列并阻止正式索引被替换；启用 OCR 后，同一命令会继续处理这些文件。
台账目录还会生成 `ocr-queue.jsonl` 和 `duplicate-groups.jsonl`：前者列出页数、大小和
推荐的小样本，后者将重复校验值映射到具体文件名，而不是只给出难以人工判断的哈希值。

### 4.1 建立批次

第一批建议选择 20～50 份已经确认可用于当前内网测试、且权限等级一致的资料，优先包含：

- 文字可直接提取的 PDF；
- 普通 DOCX；
- 目录 XLSX；
- 少量扫描 PDF、混合 PDF 和复杂表格作为困难样本。

先记录文件数量、总大小、来源、权限、版本和审核人。不要直接移动或改名原件。

### 4.2 执行逐页审计

在服务器项目目录中执行：

```bash
cd ~/App/service-agent-platform
source .venv/bin/activate

python -m scripts.audit_documents \
  /home/shuncs/rag-data/batches/batch-001 \
  --pdf-page-limit 0 \
  --output data/manifests/batch-001-audit.jsonl
```

`--pdf-page-limit 0` 表示正式处理时检查全部 PDF 页面。审计只判断格式、文本层、扫描页和
内嵌图片，不会调用大模型，也不会修改原件。

需要一次性编排全部资料时，推荐使用：

```bash
python -m scripts.build_knowledge_base \
  /home/shuncs/rag-data/raw/public \
  --output-dir data/processed/full-public \
  --manifest-dir data/manifests/full-public \
  --preprocess-only
```

首次命令只处理能直接读取的资料并生成 OCR、转换和失败队列。存在未完成资料时返回码为 1，
现有正式索引保持不变。

### 4.3 首次标准化，不执行 OCR

```bash
python -m scripts.preprocess \
  /home/shuncs/rag-data/batches/batch-001 \
  --output-dir data/processed/batch-001 \
  --manifest data/manifests/batch-001-preprocess.jsonl \
  --pdf-page-limit 0 \
  --ocr-backend none
```

根据台账将结果分流：

| 状态 | 下一步 |
| --- | --- |
| `ready` | 进入人工内容质检 |
| `needs_ocr` | 整份扫描 PDF 进入 OCR 队列 |
| `partial_needs_ocr` | 对扫描页 OCR 后与文本页合并 |
| `partial_needs_image_ocr` | 判断 DOCX 图片是否包含业务信息，再决定 OCR |
| `needs_conversion` | 旧版 DOC 转换为 DOCX 或 PDF，并核对转换结果 |
| `unsupported` | 人工确认文件格式和完整性 |
| `error` | 保留错误信息，修复后重新处理 |

### 4.4 OCR 和旧格式转换

OCR 使用独立 `.venv-ocr`，不要向主 `.venv` 混装 Paddle 依赖。先用 1～3 页困难样本验证
环境，再按小批次处理。RTX 5090 上使用 PaddleOCR-VL 前必须完成驱动和 CUDA 兼容验证；
具体命令见 [OCR 部署手册](OCR部署手册.md)。

旧版 DOC 转换后必须对照原件检查标题、页码、表格、公式、批注和图片，不能只以“命令执行
成功”作为验收结果。

OCR 环境通过验收后，使用完全相同的目录续跑：

```bash
.venv-ocr/bin/python -m scripts.build_knowledge_base \
  /home/shuncs/rag-data/raw/public \
  --output-dir data/processed/full-public \
  --manifest-dir data/manifests/full-public \
  --ocr-backend paddleocr-vl \
  --ocr-device gpu:0 \
  --preprocess-only
```

普通文件会从断点恢复，实际 OCR 主要落在扫描 PDF、混合 PDF 和 DOCX 内嵌图片上。若想因
解析策略变化而强制重跑全部文件，显式增加 `--no-resume`。

### 4.5 人工质量检查

先生成自动验收报告，排除漏页、重复页码、越界页码、乱码和未解释的空白页：

```bash
.venv-ocr/bin/python -m scripts.validate_ocr_batch \
  /home/shuncs/rag-data/batches/batch-001 \
  --manifest data/manifests/batch-001-preprocess.jsonl \
  --report data/manifests/batch-001-ocr-validation.md \
  --strict
```

自动通过不代表内容准确。报告中的 `manual_review` 默认始终为 `pending`，必须完成以下人工
检查后才能在业务台账中改为通过。

每批至少抽查 10%，且每种文件类型不少于 3 份；文件数量不足 3 份时全部检查。困难样本和
OCR 文件应全部检查。重点核对：

- 标题、章节顺序和页码是否保留；
- 条款是否被截断或串页；
- 表格行、列、单位和月份是否错位；
- 是否存在乱码、漏页、重复页和错误阅读顺序；
- OCR 是否把数字、标准号、航段名和日期识别错误；
- 预处理结果能否追溯到原文件和具体位置；
- 历史版本是否被错误标记为现行版本。

### 4.6 构建批次测试索引

全量构建器会先生成候选索引，成功后自动备份并原子替换正式索引。存在未处理文件时默认拒绝
替换；不要为了绕过检查而随意使用 `--allow-incomplete`。

```bash
python -m scripts.build_knowledge_base \
  /home/shuncs/rag-data/raw/public \
  --output-dir data/processed/full-public \
  --manifest-dir data/manifests/full-public \
  --include-processed data/processed/expanded-sample \
  --chunk-size 900 \
  --overlap 120 \
  --embedding-batch-size 8
```

固定 50 题依赖当前 28 份基线资料，因此扩展索引时要同时包含
`data/processed/expanded-sample`。如果新批次中已有相同文件，应先依据校验值去重，不能把
同一资料重复导入。如果全量原始目录本身已经包含这 28 份资料，则不要再传
`--include-processed`。旧索引自动保存在 `data/backups/`，备份索引和正式资料都不能提交
Git。服务会在下一次请求时自动加载成功替换的新索引。

### 4.7 回归与业务验收

```bash
python -m unittest discover -s tests -v

python -m scripts.evaluate \
  evals/initial-20.jsonl \
  evals/expanded-30.jsonl \
  --base-url http://127.0.0.1:8001 \
  --output data/evals/batch-001-results.jsonl \
  --summary data/evals/batch-001-summary.json
```

验收要求：

1. 现有 50 题不得出现无解释退化。
2. 每份新增的关键资料至少增加 1 道可客观验证的问题。
3. 数值和表格问题必须核对指定行、列、单位和年月。
4. 无答案问题不得因为资料增加而开始编造。
5. 业务审核人确认回答和引用后，批次才能标记为可发布。

## 5. 当前候选资料的处理优先级

2026-09-21 已对 287 份候选资料完成不执行 OCR 的逐页预处理。当前结果为 208 份 `ready`、
71 份 `needs_ocr` 和 8 份 `partial_needs_ocr`；79 份未完成资料使正式索引保持不变。
17 份旧版 DOC 均已通过 `textutil` 转换成功，最短提取正文为 3,157 字；无扩展名文件实际
是 4 页 PDF，现已正常识别。51 份 DOCX 的内嵌图片是完全相同且经人工核验的 74×74 国徽
小图，依据内容校验值记录为装饰图片，不再进入 OCR；其他未知小图仍进入 OCR 或人工检查。
共发现 10 组内容校验值重复文件，需在正式入库前由业务
人员确认保留名称和版本。建议按以下顺序处理：

同日已在升级后的双 RTX 5090 服务器完成 PaddleOCR-VL 1.6 先导与批量验证：10 份 PDF、
141 页全部通过自动验收，其中 130 页有 OCR 内容、11 页为确认纯白空白页，共提取 362,945
个字符、69 个 HTML 表格和 57 个图片引用。该结果证明技术流水线可用，但 10 份文档的
`manual_review` 仍为 `pending`，尚不能直接进入正式索引。

1. 先处理文本型 PDF、普通 DOCX 和 XLSX，建立大部分可检索内容。
2. 从 `ocr-queue.jsonl` 中选择标记为 `recommended_for_pilot` 的 1～3 页扫描件，验证
   5090 OCR 环境，再分批处理 71 份扫描 PDF 和 8 份混合 PDF。
3. 人工抽查已经转换的 17 份旧版 DOC，重点核对表格、公式、页码和批注。
4. 根据 `duplicate-groups.jsonl` 人工确认 10 组重复文件应保留的名称和版本。
5. 最后处理跨页复杂表格并完成全量质检，验收后才构建正式索引。

## 6. 本阶段完成标准

数据预处理阶段不是以“所有命令都运行过”为完成标准，而应交付：

- 原始资料台账和权限分级结果；
- 每批输入文件清单及校验值；
- 可追溯的标准 Markdown 或结构化表格；
- OCR、转换、失败和人工修订记录；
- 业务审核人与审核结论；
- 可重复执行的索引构建清单；
- 固定回归结果及新增业务评测题；
- 上一版本索引的可恢复备份。

在这些内容没有完成前，不建议将全部候选资料直接作为面向用户的正式知识库。
