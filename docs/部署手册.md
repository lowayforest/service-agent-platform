# 航道对外服务智能体部署手册

> 适用版本：本地最小 RAG MVP 0.1.0
> 更新日期：2026-09-17
> 适用对象：开发人员、服务器管理员、运维人员

## 1. 部署结论

当前推荐分两步部署：

1. 本地 Mac 和双 RTX 5090 服务器先使用 Ollama，完整兼容现有代码，用来验证资料解析、检索、回答质量和模型选型。
2. 生产化阶段再将生成模型迁移到 vLLM，以获得更好的并发和监控能力。当前代码尚未实现 OpenAI 兼容的 vLLM 客户端，迁移前需要增加适配器；向量模型可以继续由独立 Ollama 服务承载。

不要把 vLLM 地址直接填写到 `OLLAMA_BASE_URL`。现有客户端调用的是 Ollama 专用的 `/api/chat` 和 `/api/embed`，接口协议不同。

## 2. 当前部署架构

```text
用户或测试程序
       │ HTTP :8000
       ▼
FastAPI RAG 服务
  ├─ 文档解析与实时问题边界
  ├─ 本地 JSON 向量索引 data/index.json
  ├─ 混合检索与提示词组装
  └─ 来源引用整理
       │
       │ Ollama API :11434
       ▼
Ollama
  ├─ Qwen3.5-9B / 27B：回答生成
  └─ Qwen3-Embedding-0.6B：文档与问题向量化
```

端口用途：

| 端口 | 服务 | 暴露建议 |
| ---: | --- | --- |
| `8000` | FastAPI RAG API | PoC 仅内网；生产应经过认证和反向代理 |
| `11434` | Ollama | 与应用同机时只监听本机，不应直接对公网开放 |
| `8100` | 规划中的 vLLM API | 仅内网，并增加访问控制 |

## 3. 部署状态说明

| 环境 | 状态 | 模型 | 说明 |
| --- | --- | --- | --- |
| Apple M5、16 GB Mac | 已验证 | `qwen3.5:9b` + `qwen3-embedding:0.6b` | 适合开发和低并发演示 |
| 双 RTX 5090 Linux 服务器 + Ollama | 硬件已检查，软件待部署 | 首测 `qwen3.5:9b`，再评估 27B | 当前代码可直接兼容 |
| 双 RTX 5090 Linux 服务器 + vLLM | 规划 | 优先 `Qwen3.5-27B-FP8` | 需要增加应用客户端适配器 |
| Apple M5 + PP-OCRv5 mobile | 已验证 | 轻量 OCR | 适合流程验证，不保留复杂表格结构 |
| RTX 5090 + PaddleOCR-VL | 代码已接入，待服务器验证 | `PaddleOCR-VL-1.6` | 需要 Blackwell/CUDA 12.9 兼容环境 |

## 4. 本地 Mac 部署

### 4.1 安装与启动 Ollama

```bash
brew install ollama
brew services start ollama
ollama pull qwen3.5:9b
ollama pull qwen3-embedding:0.6b
```

验证：

```bash
curl http://127.0.0.1:11434/api/version
ollama list
```

### 4.2 安装应用

```bash
cd /Users/a-void/Code/service-agent-platform
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
cp .env.example .env
```

### 4.3 建索引并启动

```bash
python -m scripts.ingest README.md
uvicorn app.main:app --host 127.0.0.1 --port 8000
```

开发时可增加 `--reload`；稳定运行时不要开启自动重载。

## 5. 双 RTX 5090 服务器部署前检查

2026-09-17 已完成一次只读检查：服务器为 Ubuntu 20.04.6 LTS、x86_64，
2 × Xeon Platinum 8481C、251 GiB 内存、2 × RTX 5090（单卡 32,607 MiB），
NVIDIA 驱动为 570.133.07。两卡分属不同 NUMA 节点，拓扑为 `SYS`。
当前未安装 CUDA Toolkit、Docker、NVIDIA Container Toolkit、Conda 或 Ollama。

OCR 需要特别注意：RTX 5090 属于 Blackwell 架构，PaddleOCR 官方路径要求 NVIDIA 驱动
支持 CUDA 12.9 或以上；当前 `nvidia-smi` 只显示 CUDA 12.8，因此不能直接开始
PaddleOCR-VL GPU 部署。应先由服务器管理员评估并执行驱动升级，再安装 Docker/NVIDIA
Container Toolkit 或 CUDA 12.9 对应的 PaddlePaddle。不要在未确认其他课题组任务的情况下自行升级驱动。
完整步骤见 [OCR 部署手册](OCR部署手册.md)。

以下命令仍应保留为每次环境改动后的基线采集：

服务器到手后先保存以下输出，不要立即安装或升级驱动：

```bash
uname -a
cat /etc/os-release
lscpu
free -h
df -h
nvidia-smi
nvidia-smi topo -m
nvcc --version
docker version
```

重点确认：

- 两张卡的实际显存容量和健康状态。
- NVIDIA 驱动版本及其支持的 CUDA 版本。
- 两卡之间的 PCIe 拓扑；消费级 5090 不能按“自动合并成一块显存”理解。
- 系统内存、模型盘剩余空间、下载网络和模型缓存目录。
- 是否已经安装 Docker 和 NVIDIA Container Toolkit。
- 服务器是否只在内网开放，谁能够访问 API 和原始资料。

若 `nvidia-smi` 本身失败，先解决驱动问题，不要继续模型部署。

## 6. 双 5090 的第一阶段部署：Ollama

这是与当前应用兼容的路线。**先完成 RAG 闭环，再部署 VL OCR**；RAG 首测不需要
先安装 PaddlePaddle、Docker 或 vLLM。下面的命令都由部署人员在服务器上执行，
不需要在本机运行重型模型。

### 6.0 环境选择与执行顺序

本项目选 **Python 3.12 + `.venv`**，OCR 另建 `.venv-ocr`。`.venv` 是 Python
自带的包隔离环境，不负责安装 Python 本身，也不会包含 Ollama 模型或 NVIDIA 驱动。
服务器目前没有 Conda，没有必要为了这两个 Python 环境额外安装它。若组织已经统一使用
Conda，也可以用它创建 Python 3.12 环境，但不要在同一个环境里混装 RAG 与 OCR 的依赖。

Ubuntu 20.04 的系统 `python3` 可能低于本项目要求；**不要修改系统 Python 的软链接**。
先检查 `python3.12 --version`。若命令不存在，请管理员提供 Python 3.12 及 `venv`
组件，或与管理员商定用户级 Conda 方案，然后再继续。不要用 `sudo pip install`。

建议依次完成：

1. 用 `git status --short` 确认服务器项目目录没有未保存修改，再 `git pull --ff-only`。
2. 检查 `python3.12 --version`、`nvidia-smi`、磁盘空间和网络。
3. 安装/启动 Ollama，先下载 9B 生成模型及 0.6B 向量模型。
4. 创建主 `.venv`、安装依赖、用 README 建演示索引。
5. 仅监听 `127.0.0.1` 启动 API，完成健康检查、问答与实时问题拦截测试。
6. 获得资料使用许可后，才导入真实资料；VL OCR 按独立手册另行部署。

`git pull` 只获取已推送的代码，**不会带来本机 `profile/` 原始资料、`.env`、
`.venv`、模型缓存和 `data/index.json`**。服务器上的测试资料应由授权渠道放在
受控目录，不要通过 Git 上传。

### 6.1 安装 Ollama

Linux 官方安装入口当前提供：

```bash
curl -fsSL https://ollama.com/install.sh | sh
sudo systemctl enable --now ollama
sudo systemctl status ollama
```

生产环境应在执行远程脚本前由运维审核脚本内容，也可以按官方文档使用固定版本或手动安装。

### 6.2 下载模型

```bash
ollama pull qwen3.5:9b
ollama pull qwen3-embedding:0.6b
ollama list
```

确认 9B 的检索和问答都正常后，再选做 `ollama pull qwen3.5:27b`，并修改
`.env` 的 `CHAT_MODEL`。27B 的质量与显存表现需要同一测试集评估，不能只因服务器有
两张卡就直接认为必须使用 27B。

### 6.3 验证 GPU 使用

启动一次问答后执行：

```bash
ollama ps
nvidia-smi
```

需要确认模型没有大量回退到 CPU，并记录单卡或双卡的实际分布。是否采用两卡不是由模型名称决定，而应由显存、上下文、并发和吞吐测试决定。

### 6.4 部署应用

先进入服务器上**实际的项目目录**（即有 `README.md` 和 `requirements.txt` 的目录）。
不要直接复制下面的示例目录路径；进入后用 `pwd` 确认位置。然后执行：

```bash
python3.12 --version
python3.12 -m venv .venv
source .venv/bin/activate
python --version
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
cp .env.example .env
```

`.env` 默认是 9B 和本机 Ollama，可先保持原样。若需要手动核对，应为：

```dotenv
OLLAMA_BASE_URL=http://127.0.0.1:11434
CHAT_MODEL=qwen3.5:9b
EMBEDDING_MODEL=qwen3-embedding:0.6b
INDEX_PATH=data/index.json
RAG_TOP_K=4
RAG_NUM_CTX=8192
OLLAMA_TIMEOUT=600
```

首次测试使用 8K 上下文。只有质量评测确实需要时再增加到 16K，不要在未测显存的情况下直接使用模型支持的最大上下文。

### 6.5 构建服务器索引

先用公开的 README 做无敏感资料演示：

```bash
python -m scripts.ingest README.md
```

看到“索引构建完成”后，再按授权范围把首批样本放入受控目录，并明确指定：

```bash
python -m scripts.ingest \
  "/受控资料目录/法规样本" \
  "/受控资料目录/标准样本"
```

每次 `scripts.ingest` 都会用本次指定的资料**重建** `data/index.json`；
第二次命令不会自动保留第一次 README 的内容。原始资料、生成索引和日志都不应提交到代码仓库。

### 6.6 启动应用

PoC 首先只在服务器本机手工启动：

```bash
uvicorn app.main:app --host 127.0.0.1 --port 8000 --workers 1
```

这个终端需要保持运行；另开 SSH 终端执行第 8 节的 `curl` 检查。确认功能后，
若确实需要从自己电脑访问，优先使用 SSH 端口转发；不要把当前无认证接口直接绑定
`0.0.0.0` 暴露到内网或公网。按 `Ctrl+C` 可停止手工服务。

### 6.7 systemd 示例

在正式服务器上可以由运维创建 `/etc/systemd/system/service-agent-rag.service`：

```ini
[Unit]
Description=Service Agent RAG API
After=network-online.target ollama.service
Wants=network-online.target

[Service]
Type=simple
User=service-agent
Group=service-agent
WorkingDirectory=/opt/service-agent-platform
EnvironmentFile=/opt/service-agent-platform/.env
ExecStart=/opt/service-agent-platform/.venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8000 --workers 1
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
```

用户、用户组、目录权限和反向代理应由运维根据实际环境创建。确认内容后再执行：

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now service-agent-rag
sudo systemctl status service-agent-rag
journalctl -u service-agent-rag -f
```

## 7. vLLM 生产化路线

### 7.1 当前限制

vLLM 提供 OpenAI 兼容接口，而当前项目使用 Ollama 专用接口。因此迁移需要增加以下配置和代码能力：

```text
CHAT_BACKEND=ollama | openai
CHAT_BASE_URL=http://127.0.0.1:8100/v1
CHAT_API_KEY=受控密钥
CHAT_MODEL=Qwen/Qwen3.5-27B-FP8
```

同时保留独立的 `EMBEDDING_BASE_URL`，不能再假设生成和向量服务使用同一个地址。

### 7.2 试验命令

Qwen 官方模型卡说明 Qwen3.5 可通过 vLLM 服务。双卡 5090 上可从下面的保守参数开始试验：

```bash
CUDA_VISIBLE_DEVICES=0,1 vllm serve Qwen/Qwen3.5-27B-FP8 \
  --host 127.0.0.1 \
  --port 8100 \
  --tensor-parallel-size 2 \
  --max-model-len 8192 \
  --gpu-memory-utilization 0.85 \
  --reasoning-parser qwen3
```

这是待服务器验证的起点，不是已经确认可用的生产参数。当前 Qwen3.5 官方说明可能要求使用较新的 vLLM 构建；应在独立虚拟环境中按官方模型卡和 vLLM Qwen3.5 recipe 锁定一个经过测试的版本。

验证 OpenAI 兼容接口：

```bash
curl http://127.0.0.1:8100/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{
    "model":"Qwen/Qwen3.5-27B-FP8",
    "messages":[{"role":"user","content":"请回答：1+1等于多少？"}],
    "temperature":0
  }'
```

如果出现显存不足，按顺序处理：

1. 将 `--max-model-len` 降低到 4096。
2. 下调并发和批处理参数。
3. 检查是否存在其他 GPU 进程。
4. 评估 AWQ/GPTQ 等量化版本或回退 9B。
5. 不要简单增加交换空间掩盖显存规划问题。

## 8. 部署验收

### 8.1 基础检查

```bash
curl http://127.0.0.1:11434/api/version
curl http://127.0.0.1:8000/api/health
ollama ps
nvidia-smi
```

健康检查应显示正确的生成模型、向量模型和大于 0 的 `indexed_chunks`。

### 8.2 功能检查

```bash
curl -X POST http://127.0.0.1:8000/api/chat \
  -H 'Content-Type: application/json' \
  -d '{"question":"第一阶段为什么先做知识库问答？"}'
```

确认回答包含有效的 `[S1]` 引用，并且引用编号存在于 `sources`。

实时问题检查：

```bash
curl -X POST http://127.0.0.1:8000/api/chat \
  -H 'Content-Type: application/json' \
  -d '{"question":"今天某航段实时水深是多少？"}'
```

应返回 `blocked_realtime=true`，不得出现具体水深。

### 8.3 性能基线

至少记录：

- 冷启动完整响应时间。
- 热启动首字延迟和完整响应时间。
- 输出 token/s。
- 8K 与 16K 上下文的显存变化。
- 单并发、2 并发、4 并发的成功率和延迟。
- 9B、27B 使用同一评测集时的正确率、引用正确率和拒答正确率。

第一轮不要只测聊天速度。RAG 项目的核心指标是检索、引用和拒答是否正确。

## 9. 安全要求

- 原始资料目录、`data/index.json`、`.env` 和日志不得进入 Git。
- 当前 API 没有身份认证，只允许本机或受控内网测试。
- Ollama 和 vLLM 不应直接暴露公网。
- 对外服务前必须增加 TLS、认证、限流、文件权限、审计日志和提示注入测试。
- 公共资料与内部资料应使用不同索引或强制权限过滤，不能只在提示词里声明权限。
- 资料更新前应记录文件校验值、版本、有效期和审核人。
- 动态数据必须来自权威接口并显示时间戳；接口失败时不得回退到历史数值。

## 10. 更新与回滚

部署前保存：

- 当前 Git 提交号。
- `.env` 的受控备份。
- 模型名称和 `ollama show` 输出。
- 索引构建所使用的文件清单与构建时间。
- 业务评测结果。

应用回滚应切回已验证的 Git 提交和配置。索引是可重建数据，优先通过原始资料清单重新构建；如果需要快速恢复，应将上一版索引复制到受控备份目录，而不是提交 Git。
