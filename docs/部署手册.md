# 航道对外服务智能体部署手册

> 适用版本：RAG 基线与 vLLM 生产适配 0.1.0
>
> 更新日期：2026-09-24
>
> 适用对象：开发人员、服务器管理员、运维人员

## 1. 部署结论

当前推荐分三步部署：

1. 本地 Mac 和双 RTX 5090 服务器保留 Ollama 基线，用来验证资料解析、检索和回答质量。
2. 双 RTX 5090 使用标准 vLLM 验证 OpenAI 兼容接口、模型质量、索引重建和并发，不把 CUDA 环境当作最终生产环境。
3. 长江航道局目标服务器使用 vLLM-Ascend。应用继续调用相同的 OpenAI Chat Completions 和 Embeddings 接口，不修改 RAG 业务代码。

代码已经实现 Ollama 与 OpenAI 兼容客户端，并允许生成和向量后端分别配置。生产模板见
`.env.vllm.example`，硬件与模型的冻结方案见 [vLLM 最终部署方案](vLLM最终部署方案.md)。
不要把 vLLM 地址写入旧版 `OLLAMA_BASE_URL`；应设置 `CHAT_BACKEND=openai` 和
`EMBEDDING_BACKEND=openai`，且两个 URL 都要包含 `/v1`。

## 2. 当前部署架构

```text
用户或测试程序
       │ HTTP :8001
       ▼
FastAPI RAG 服务 :8001
  ├─ 文档解析与实时问题边界
  ├─ 本地 JSON 向量索引 data/index.json
  ├─ 混合检索与提示词组装
  └─ 来源引用整理
       ├─ 开发/回退：Ollama :11434
       ├─ 生产生成：OpenAI Chat Completions :8100/v1
       └─ 生产向量：OpenAI Embeddings :8101/v1

双 5090：标准 vLLM
目标 Atlas 300I Duo：vLLM-Ascend
```

端口用途：

| 端口 | 服务 | 暴露建议 |
| ---: | --- | --- |
| `8001` | FastAPI RAG API | PoC 仅内网；生产应经过认证和反向代理 |
| `11434` | Ollama | 与应用同机时只监听本机，不应直接对公网开放 |
| `8100` | vLLM/vLLM-Ascend 生成 API | 只监听本机或受控服务网段，并设置 API key |
| `8101` | vLLM/vLLM-Ascend 向量 API | 只监听本机或受控服务网段，并设置 API key |

### 4.1 安装与启动 Ollama

```bash
brew install ollama
brew services start ollama
ollama pull qwen3.5:9b
ollama pull qwen3-embedding:0.6b
```

验证：

```bash
curl http://127.0.0.1:11434/api/version
ollama list
```

### 4.2 安装应用

```bash
cd /Users/a-void/Code/service-agent-platform
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
cp .env.example .env
```

### 4.3 建索引并启动

```bash
python -m scripts.ingest README.md
uvicorn app.main:app --host 127.0.0.1 --port 8001
```

开发时可增加 `--reload`；稳定运行时不要开启自动重载。

## 5. 双 RTX 5090 服务器部署前检查

2026-09-21 已完成硬件与 OCR 运行环境复核：服务器为 Ubuntu 20.04.6 LTS、x86_64，
2 × Xeon Platinum 8481C、251 GiB 内存、2 × RTX 5090（单卡 32,607 MiB），
当前 NVIDIA 驱动为 580.126.09，Paddle 实测 Driver API / Runtime API 为 13.0 / 12.9。
两卡分属不同 NUMA 节点，
拓扑为 `SYS`。
当前已经安装并运行 Ollama，`qwen3.5:9b`、`qwen3-embedding:0.6b` 与应用 API 已完成验证。
PaddleOCR-VL 批处理链路也已验证；Conda 不是本项目必需依赖。

OCR 需要特别注意：RTX 5090 属于 Blackwell 架构，当前已经在 Driver API 13 / Runtime
12.9 环境完成验证。不得为了 vLLM 随意变更已验证的驱动、PaddlePaddle 或 OCR 环境；标准
vLLM 应使用独立虚拟环境或容器，并在变更后重新跑 OCR 与 RAG 回归。
完整步骤见 [OCR 部署手册](OCR部署手册.md)。

以下命令仍应保留为每次环境改动后的基线采集：

服务器到手后先保存以下输出，不要立即安装或升级驱动：

```bash
uname -a
cat /etc/os-release
lscpu
free -h
df -h
nvidia-smi
nvidia-smi topo -m
nvcc --version
docker version
```

重点确认：

- 两张卡的实际显存容量和健康状态。
- NVIDIA 驱动版本及其支持的 CUDA 版本。
- 两卡之间的 PCIe 拓扑；消费级 5090 不能按“自动合并成一块显存”理解。
- 系统内存、模型盘剩余空间、下载网络和模型缓存目录。
- 是否已经安装 Docker 和 NVIDIA Container Toolkit。
- 服务器是否只在内网开放，谁能够访问 API 和原始资料。

若 `nvidia-smi` 本身失败，先解决驱动问题，不要继续模型部署。

## 6. 双 5090 的第一阶段部署：Ollama

这是与当前应用兼容的路线。**先完成 RAG 闭环，再部署 VL OCR**；RAG 首测不需要
先安装 PaddlePaddle、Docker 或 vLLM。下面的命令都由部署人员在服务器上执行，
不需要在本机运行重型模型。

### 6.0 环境选择与执行顺序

本项目选 **Python 3.12 + `.venv`**，OCR 另建 `.venv-ocr`。`.venv` 是 Python
自带的包隔离环境，不负责安装 Python 本身，也不会包含 Ollama 模型或 NVIDIA 驱动。
服务器目前没有 Conda，没有必要为了这两个 Python 环境额外安装它。若组织已经统一使用
Conda，也可以用它创建 Python 3.12 环境，但不要在同一个环境里混装 RAG 与 OCR 的依赖。

Ubuntu 20.04 的系统 `python3` 可能低于本项目要求；**不要修改系统 Python 的软链接**。
先检查 `python3.12 --version`。若命令不存在，请管理员提供 Python 3.12 及 `venv`
组件，或与管理员商定用户级 Conda 方案，然后再继续。不要用 `sudo pip install`。

建议依次完成：

1. 用 `git status --short` 确认服务器项目目录没有未保存修改，再 `git pull --ff-only`。
2. 检查 `python3.12 --version`、`nvidia-smi`、磁盘空间和网络。
3. 安装/启动 Ollama，先下载 9B 生成模型及 0.6B 向量模型。
4. 创建主 `.venv`、安装依赖、用 README 建演示索引。
5. 仅监听 `127.0.0.1` 启动 API，完成健康检查、问答与实时问题拦截测试。
6. 获得资料使用许可后，才导入真实资料；VL OCR 按独立手册另行部署。

`git pull` 只获取已推送的代码，**不会带来本机 `profile/` 原始资料、`.env`、
`.venv`、模型缓存和 `data/index.json`**。服务器上的测试资料应由授权渠道放在
受控目录，不要通过 Git 上传。

### 6.1 安装 Ollama

Linux 官方安装入口当前提供：

```bash
curl -fsSL https://ollama.com/install.sh | sh
sudo systemctl enable --now ollama
sudo systemctl status ollama
```

生产环境应在执行远程脚本前由运维审核脚本内容，也可以按官方文档使用固定版本或手动安装。

### 6.2 下载模型

```bash
ollama pull qwen3.5:9b
ollama pull qwen3-embedding:0.6b
ollama list
```

确认 9B 的检索和问答都正常后，再选做 `ollama pull qwen3.5:27b`，并修改
`.env` 的 `CHAT_MODEL`。27B 的质量与显存表现需要同一测试集评估，不能只因服务器有
两张卡就直接认为必须使用 27B。

### 6.3 验证 GPU 使用

启动一次问答后执行：

```bash
ollama ps
nvidia-smi
```

需要确认模型没有大量回退到 CPU，并记录单卡或双卡的实际分布。是否采用两卡不是由模型名称决定，而应由显存、上下文、并发和吞吐测试决定。

### 6.4 部署应用

先进入服务器上**实际的项目目录**（即有 `README.md` 和 `requirements.txt` 的目录）。
不要直接复制下面的示例目录路径；进入后用 `pwd` 确认位置。然后执行：

```bash
python3.12 --version
python3.12 -m venv .venv
source .venv/bin/activate
python --version
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
cp .env.example .env
```

`.env` 默认是 9B 和本机 Ollama，可先保持原样。若需要手动核对，应为：

```dotenv
CHAT_BACKEND=ollama
CHAT_BASE_URL=http://127.0.0.1:11434
CHAT_MODEL=qwen3.5:9b
CHAT_ENABLE_THINKING=false
EMBEDDING_BACKEND=ollama
EMBEDDING_BASE_URL=http://127.0.0.1:11434
EMBEDDING_MODEL=qwen3-embedding:0.6b
INDEX_PATH=data/index.json
RAG_TOP_K=4
RAG_MIN_SCORE=0.45
RAG_NUM_CTX=8192
RAG_TEMPERATURE=0
RAG_SEED=42
RAG_MAX_TOKENS=600
MODEL_TIMEOUT=600
```

首次测试使用 8K 上下文。只有质量评测确实需要时再增加到 16K，不要在未测显存的情况下直接使用模型支持的最大上下文。
最低相关度默认保持 `0.45`；如果所有候选片段都低于该值，服务会直接拒答，不再让模型根据弱相关资料生成答案。

### 6.5 构建服务器索引

先用公开的 README 做无敏感资料演示：

```bash
python -m scripts.ingest README.md
```

看到“索引构建完成”后，再按授权范围把首批样本放入受控目录，并明确指定：

```bash
python -m scripts.ingest \
  "/受控资料目录/法规样本" \
  "/受控资料目录/标准样本"
```

每次 `scripts.ingest` 都会用本次指定的资料**重建** `data/index.json`；
第二次命令不会自动保留第一次 README 的内容。原始资料、生成索引和日志都不应提交到代码仓库。

### 6.6 启动应用

PoC 首先只在服务器本机手工启动：

```bash
uvicorn app.main:app --host 127.0.0.1 --port 8001 --workers 1
```

这个终端需要保持运行；另开 SSH 终端执行第 8 节的 `curl` 检查。确认功能后，
若确实需要从自己电脑访问，优先使用 SSH 端口转发；不要把当前无认证接口直接绑定
`0.0.0.0` 暴露到内网或公网。按 `Ctrl+C` 可停止手工服务。

当前实验室服务器为了同一受控局域网内的人工测试，使用 Screen 监听 `8001`：

```bash
cd ~/App/service-agent-platform
screen -L -Logfile "$PWD/logs/rag-api.log" -dmS rag-api \
  .venv/bin/python -m uvicorn app.main:app \
  --host 0.0.0.0 --port 8001 --workers 1
```

局域网访问地址为 `http://10.98.196.218:8001/docs`。此方式没有认证，只适用于已经确认网络
边界和访问人员的测试阶段；不得映射到公网。停止或重启时先执行：

```bash
screen -S rag-api -X quit
```

正式部署仍应改用 systemd，并通过反向代理提供 TLS、身份认证、访问控制和限流。

### 6.7 systemd 示例

在正式服务器上可以由运维创建 `/etc/systemd/system/service-agent-rag.service`：

```ini
[Unit]
Description=Service Agent RAG API
After=network-online.target ollama.service
Wants=network-online.target

[Service]
Type=simple
User=service-agent
Group=service-agent
WorkingDirectory=/opt/service-agent-platform
EnvironmentFile=/opt/service-agent-platform/.env
ExecStart=/opt/service-agent-platform/.venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8001 --workers 1
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
```

用户、用户组、目录权限和反向代理应由运维根据实际环境创建。确认内容后再执行：

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now service-agent-rag
sudo systemctl status service-agent-rag
journalctl -u service-agent-rag -f
```

## 7. vLLM 生产化路线

本节只说明操作顺序。模型、版本、目标服务器限制、验收和回滚的唯一详细依据是
[vLLM 最终部署方案](vLLM最终部署方案.md)。

### 7.1 已实现的应用边界

当前代码已经支持 OpenAI 兼容的生成与向量接口，两个服务必须独立配置：

```dotenv
CHAT_BACKEND=openai
CHAT_BASE_URL=http://127.0.0.1:8100/v1
CHAT_API_KEY=受控密钥
CHAT_MODEL=qwen3.5

EMBEDDING_BACKEND=openai
EMBEDDING_BASE_URL=http://127.0.0.1:8101/v1
EMBEDDING_API_KEY=受控密钥
EMBEDDING_MODEL=qwen3-embedding

INDEX_PATH=data/index-vllm.json
```

可直接执行 `cp .env.vllm.example .env` 后填写密钥。健康检查会同时显示生成和向量后端。
从 Ollama 改为 vLLM 向量服务后，必须完整重建 `data/index-vllm.json`；代码会校验索引中的
`embedding_backend` 与 `embedding_model`，不允许误用旧索引。

### 7.2 双 5090 验证顺序

双 5090 只用于标准 vLLM 验证，不代表目标生产硬件。按以下顺序执行：

1. 在独立 `.venv-vllm` 或容器中安装经过锁定的标准 vLLM，不污染 `.venv` 和 `.venv-ocr`。
2. GPU 0 启动 `Qwen3.5-9B` 生成服务，GPU 1 启动 `Qwen3-Embedding-0.6B` 向量服务。
3. 验证 `/v1/chat/completions`、`/v1/embeddings` 和 API key。
4. 使用新向量端点重建独立索引，运行固定 50 题及 OCR 业务题。
5. 再做单并发、2 并发、4 并发压测；通过后才评估 27B。

完整的标准 vLLM 启动命令已经写入最终方案，不能把其中的 CUDA 参数用于 Atlas 服务器。

### 7.3 Atlas 目标服务器路线

Huanghe 2280 V2 使用 4 张 Atlas 300I Duo，必须使用 310P 对应的 vLLM-Ascend，不安装
CUDA 版 vLLM。第一生产候选固定为 `Qwen3.5-9B FP16`，当前建议兼容基线为：

| 组件 | 冻结起点 |
| --- | --- |
| vLLM-Ascend | `0.23.0` |
| Ubuntu 镜像 | `quay.io/ascend/vllm-ascend:v0.23.0-310p` |
| openEuler 镜像 | `quay.io/ascend/vllm-ascend:v0.23.0-310p-openeuler` |
| CANN | `9.1.0` |
| PyTorch / TorchNPU | `2.10.0` / `2.10.0.post4` |
| 模型数据类型 | FP16 |

部署前先采集 OS、昇腾驱动、固件、CANN、`npu-smi info`、`/dev/davinci*` 和拓扑，再按
现场 OS 选择镜像并记录 digest。Atlas 300I Duo 的 Qwen3.5 启动必须使用 `--dtype float16`、
`--mamba-ssm-cache-dtype float16`，并关闭不受支持的 `npugraph_ex`。设备挂载数量必须以现场
枚举为准，不能从“4 张卡”直接猜测。

Qwen3-Embedding 在该硬件上属于实验支持，所以 :8101 必须独立完成向量维度、批量顺序、
中文召回和稳定性验收；不通过时只替换向量服务实现，不改应用 API。27B 仅是后续候选，
只有 9B 通过同一套业务评测和压测后才进入对照试验。

## 8. 部署验收

### 8.1 基础检查

```bash
curl http://127.0.0.1:11434/api/version
curl http://127.0.0.1:8001/api/health
ollama ps
nvidia-smi
```

上述命令适用于 Ollama 基线。vLLM 环境改为检查两个模型端点：

```bash
curl -H "Authorization: Bearer $CHAT_API_KEY" http://127.0.0.1:8100/v1/models
curl -H "Authorization: Bearer $EMBEDDING_API_KEY" http://127.0.0.1:8101/v1/models
curl http://127.0.0.1:8001/api/health
```

Atlas 目标机另用 `npu-smi info` 检查设备，不运行 `nvidia-smi`。

健康检查应显示正确的生成模型、向量模型和大于 0 的 `indexed_chunks`。

### 8.2 功能检查

```bash
curl -X POST http://127.0.0.1:8001/api/chat \
  -H 'Content-Type: application/json' \
  -d '{"question":"第一阶段为什么先做知识库问答？"}'
```

确认回答包含有效的 `[S1]` 引用，并且引用编号存在于 `sources`。

实时问题检查：

```bash
curl -X POST http://127.0.0.1:8001/api/chat \
  -H 'Content-Type: application/json' \
  -d '{"question":"今天某航段实时水深是多少？"}'
```

应返回 `blocked_realtime=true`，不得出现具体水深。

### 8.3 性能基线

至少记录：

- 冷启动完整响应时间。
- 热启动首字延迟和完整响应时间。
- 输出 token/s。
- 8K 与 16K 上下文的显存变化。
- 单并发、2 并发、4 并发的成功率和延迟。
- 9B、27B 使用同一评测集时的正确率、引用正确率和拒答正确率。

第一轮不要只测聊天速度。RAG 项目的核心指标是检索、引用和拒答是否正确。

## 9. 安全要求

- 原始资料目录、`data/index.json`、`.env` 和日志不得进入 Git。
- 当前 API 没有身份认证，只允许本机或受控内网测试。
- Ollama 和 vLLM 不应直接暴露公网。
- 对外服务前必须增加 TLS、认证、限流、文件权限、审计日志和提示注入测试。
- 公共资料与内部资料应使用不同索引或强制权限过滤，不能只在提示词里声明权限。
- 资料更新前应记录文件校验值、版本、有效期和审核人。
- 动态数据必须来自权威接口并显示时间戳；接口失败时不得回退到历史数值。

## 10. 更新与回滚

部署前保存：

- 当前 Git 提交号。
- `.env` 的受控备份。
- 模型名称和 `ollama show` 输出。
